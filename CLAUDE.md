# Darasa360 — Finance + Academics Monorepo

Two Laravel apps sharing a platform DB, deployed to a shared-hosting DirectAdmin/CloudLinux server. Solo-maintained — this file plus the two skills below (`deploy-to-live`, `debug-darasa`) are the persistent knowledge base across sessions. Read this before touching deployment, migrations, or server config.

**Never put real credentials, passwords, or API keys in this file or in the skills below — this repo is committed to git.** Credentials live in Claude's memory (`project_darasa_finance.md`, project type) and in each server's `.env` files, not here.

## Layout
- `finance/` and `academics/` — two independent Laravel apps, each with its own `composer.json`/`package.json`/`.env`
- Shared `platform` DB (schools registry, super admin, SSO tokens) — Finance owns the platform migrations (`finance/database/migrations/platform/`)
- Each app has a `tenant` DB connection for per-school databases, auto-provisioned via the DirectAdmin API (see `DA_*` env vars)
- Academics has a separate per-school migration path (`academics/database/migrations/school/`) applied via `php artisan migrate:schools` (see `app/Console/Commands/MigrateAllSchools.php`) — **not** picked up by the normal `php artisan migrate`
- Finance similarly has `finance/database/migrations/central/` for its own central-DB tables (`super_admins`, `schools`, `school_accountants`, `activity_logs`, `analytics_summary`) — run via `php artisan migrate --path=database/migrations/central`, also not picked up by the normal sweep
- Each school gets its **own dedicated MySQL user + password** (via `DirectAdminService::createDatabase()`, stored on the school record as `db_username`/`db_password`) — this host does not support granting one shared user access to arbitrary databases, so there is no shared-credential fallback that actually works for real schools (see "Resolved" section below for the full history of why)

## Branches
- `sandbox` — day-to-day development, deployed to `*-sandbox.darasa360.co.tz`
- `main` — production, deployed to `finance.darasa360.co.tz` / `academics.darasa360.co.tz`
- Workflow: commit to `sandbox` → push → `git checkout main && git merge sandbox --ff-only` → push `main` → pull on whichever live server folder(s) changed

## The #1 gotcha in this codebase
**The sandbox server sometimes has direct file edits that were never committed to git.** This has happened twice already: the entire Academics third-party template asset folder (`academics/resources/assets/vendor/`) and a full login-page redesign (`academics/resources/views/content/authentications/auth-login-basic.blade.php`) both existed only on the sandbox server's filesystem, invisible to `git log`/`git diff` on any machine, and were missed on the first live deploy because "it works on sandbox" wasn't actually backed by git.

**Before trusting that a fresh `git clone` + deploy will look/behave like sandbox, diff the sandbox server's actual files against git for anything user-facing** (blade views, public assets, config). `git status` run *on the sandbox server itself* will show these as modified/untracked — that's the tell. See the `deploy-to-live` skill for the exact commands.

## Server facts worth knowing up front
- SSH is on **port 22**. Port 2222 is the DirectAdmin control panel (HTTPS) — connecting SSH there fails at the banner-exchange stage and looks exactly like a firewall block, but isn't.
- This host's MySQL **default_storage_engine is MyISAM**, not InnoDB (unusual). `config/database.php` in both apps explicitly forces `'engine' => env('DB_ENGINE', 'InnoDB')` on every mysql connection — don't remove that, migrations with unique/long indexes will break with "max key length is 1000 bytes".
- `npm install` on this server is unreliable (CloudLinux/LVE process-limit `EAGAIN` errors from esbuild's postinstall spawning too many processes). Build frontend assets locally and upload `public/build/` via scp — don't run `npm run build` on the server itself.
- Git doesn't track empty directories: `bootstrap/cache` and several `storage/framework/*` subdirs won't exist after a fresh clone and must be created manually before `composer install`'s `package:discover` hook will succeed.
- Each domain's docroot must point at `<app>/public`, not the monorepo root — set via DirectAdmin's domain/subdomain table (a plain, user-editable "Docroot" column, not an admin-only setting).

## Fixed: Finance live .env had wrong DirectAdmin API variable names (2026-07-26)
Finance's `config/directadmin.php` reads `DA_HOST`/`DA_PORT`/`DA_USER`, but the live `.env` created during initial deployment used `DA_API_URL`/`DA_USERNAME` instead (copy-paste drift from whatever the original deployment notes had). Since `TenantDatabaseManager::createDatabase()` only calls the DirectAdmin API when `config('directadmin.user')` is non-empty, this silently made Finance's school-provisioning fall back to a raw-SQL path that doesn't work on this shared-hosting MySQL (same underlying constraint as the Academics issue below) — every new school created via Finance's admin panel on live would likely have hit this fallback. Fixed by correcting the live `.env` var names to match sandbox's (which was already correct) and re-caching config. **When creating any new environment's `.env` from a template, diff the variable names against what `config/directadmin.php` (or equivalent) actually reads — don't assume the template itself is correct.**

## Known incomplete feature: Academics→Finance super-admin cross-jump (found 2026-07-26)
The "Open Finance Admin Panel" button on Academics' super admin dashboard issues a handoff token and redirects to `{FINANCE_APP_URL}/superadmin/handoff/consume?token=...`, but Finance has no `/superadmin/handoff/consume` route at all - only `/handoff/consume` (headmaster/owner/parent roles, see `finance/app/Http/Controllers/HandoffController@consumeFromAcademics`), which has no branch for `role === 'super_admin'`. This was never actually built on the Finance side despite the Academics side existing and being wired up (its route just happened to live in a dead, unloaded routes file too - see the fix in this session's commits around `super_admin_routes.php` - so this bug was doubly hidden). Not fixed yet - needs a new Finance-side route + a `super_admin` branch in `consumeFromAcademics` (or a dedicated method) that logs into the `PlatformSuperAdmin` guard. Not blocking school onboarding, just a convenience cross-jump button.

## Resolved: Academics per-school DB provisioning was fundamentally broken (fixed 2026-07-26)
Confirmed root cause: this host's shared MySQL user does not have grants on arbitrary tenant databases, and `DatabaseHelper::createDatabaseUser()`'s raw SQL (`CREATE USER`/`GRANT`) silently failed every time (wrapped in a try/catch with a comment claiming "the main DB user has access to all databases in shared hosting" — false). Rebuilt to match Finance's already-working pattern:
- New `App\Services\DirectAdminService` (both apps) actually creates the database + a dedicated user via DirectAdmin's classic `/CMD_API_DATABASES` API (`action=create` works reliably; **its `action=delete` claims success but does nothing** — use the REST `/api/db-manage/databases/{db}` `DELETE` endpoint instead, which does work. Both services' `dropDatabase()` already use the working one.)
- `schools.db_username`/`db_password` store the real per-school credentials; `School::tenantConnectionConfig()`/`useAsTenant()` is the one canonical way to point the `tenant` connection at a school — replaced 15 separately-duplicated, inconsistent `configureTenantConnection()` implementations across controllers/middleware/commands with calls to it
- Verified end-to-end on sandbox: created a real test school via the super-admin panel, DirectAdmin provisioned a real dedicated DB+user, all 57 school-level migrations ran successfully against it, owner login worked

**Known UX gotcha:** creating a school runs 100+ migrations synchronously inside the HTTP request. This can exceed the web server's execution-time limit and show a **misleading 500 error page even though the school was actually created successfully** (verified: no Laravel exception logged, DB fully provisioned, all tables present) — always check the schools list before assuming a create failed and retrying, since retrying a "failed" create might attempt to reprovision a school that already exists. Not fixed (would need to move migration-running to a queued job) — just know to check before panicking or retrying.

**Also fixed the same underlying gap on Finance's live environment**: `finance/database/migrations/central/` (creates `super_admins`, `schools`, `school_accountants`, `activity_logs`, `analytics_summary`) had never been run against live at all — only sandbox has it, because sandbox uses a genuinely separate `central` database while live's `.env` consolidates `central` into the main database. This caused a 500 on every live Finance super-admin login (missing `school_id`/`user_type` columns on the pre-existing, differently-purposed `activity_logs` table) and would have blocked "Manage Schools"/"Activity Logs" too. Made all of `central/`'s migrations idempotent (`hasTable`/`hasColumn` guards) and ran them against live — safe to re-run anywhere now.

## Resolved (mostly): cross-system provisioning — onboarding a school into both Finance and Academics (2026-07-26/27)
Finance has a real, intentional "onboard both systems at once" feature (`has_finance`/`has_academics` checkboxes on `/superadmin/schools/create`), plus an "Enable Academics" form on an existing school's detail page for the "one system first, add the other later" case. Both were completely non-functional until this fix:

- **The bug:** `SchoolProvisioningService::provisionSchool()` (Finance) tried to run Academics' migrations *from within Finance's own PHP process* by pointing Laravel's migrator at Academics' folder path. This ran the wrong migration set (`database/migrations/`, Academics' own central/admin schema — users/roles/schools for Academics' *own* admin accounts) instead of `database/migrations/school/` (the actual per-school tenant schema — students/classes/exams/attendance/etc, same one `MigrateAllSchools` uses). It also would have run against *Finance's* `tenant` connection config, not Academics', since the migration files hardcode `Schema::connection('tenant')`. The "enable later" toggle didn't provision anything at all — just flipped a boolean. Live didn't even have the config this old code needed (`ACADEMICS_APP_PATH`/`ACADEMICS_MAIN_DB`).
- **The fix:** a proper internal HTTP API instead of cross-process migration-running. Academics provisions itself, in its own process, using its own already-correct `SchoolProvisioningService` (extracted from `SuperAdminController::createSchool()` so the web form and this API share one implementation) — see `academics/routes/internal_api.php`, guarded by a shared-secret header (`INTERNAL_API_SECRET` in both apps' `.env`, checked by `VerifyInternalApiSecret` middleware). Finance calls `POST /internal-api/schools` and, for the "enable later" case, the new `SchoolController::enableAcademics()` (not the old no-op toggle — that still exists for *disabling*, which doesn't need real provisioning).

**Residual reliability risk — genuinely unresolved, needs proper fixing:** this cross-app call runs 100+ migrations and can take minutes. This host's web server has been observed, across repeated testing, to:
1. Sometimes let the backend PHP process run to completion even after killing the client-facing connection (showing a misleading "Request Timeout" page while the work actually finishes correctly) — the same pattern as the standalone Academics create-school gotcha above.
2. But **at least once, actually killed the request mid-migration**, leaving a School row in Academics with an incomplete tenant database (missing tables) and no owner account — a genuinely broken partial state, not just a confusing success.

Because of (2), the response-reading code (`SchoolProvisioningService::provisionAcademicsSchool()`, Finance) can't just optimistically assume success when the HTTP response is unreadable — it calls Academics' `GET /internal-api/schools/exists` to check for real completion. That check deliberately verifies `school.user_id` is set (the last thing that happens, after migrations *and* owner-account creation both succeed and the transaction commits), not just that a School row exists, since the row is created *before* migrations run. If verification finds a row that exists but isn't complete, it throws a clear error telling the operator to manually clean up (drop the partial DB via DirectAdmin, delete the incomplete school row) before retrying with the same name.

**This mitigates the risk (no more silent false-positives) but doesn't eliminate it** — a request can still die mid-migration and require manual cleanup. The actual fix is architectural: move the whole provisioning flow to a queued background job so it isn't bound by any HTTP request's timeout at all. Not done — this is real, scoped follow-up work, not a quick patch (see spawned background task for it).

**Test data hygiene:** every test school created during this work was cleaned up afterward (dropped DB via the REST API — remember, not the classic API's delete — plus deleted the School/User/PlatformSchool/SchoolAccountant rows on both sides). If you see an unfamiliar school named anything test-sounding in either app's live-adjacent sandbox, check before assuming it's real data.
